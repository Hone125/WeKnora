# 课题三：embedding 缓存实验与证据边界

更新日期：2026-09-12。

## 1. 当前能证明什么

已经通过真实后端、PostgreSQL 与 SiliconFlow 进行了两次评测，两次门禁均通过。下面保留原始观察值，但不把缓存表行数当成模型请求次数。

| 阶段 | 缓存表行数 | Recall | 总 token | 总耗时 |
|---|---:|---:|---:|---:|
| 第一次评测后 | 61 | 0.500 | 48374 | 16090 ms |
| 重启后第二次评测后 | 62 | 0.533 | 48927 | 17364 ms |

本地原始结果目录分别为 `eval-results/run-x62Ttb` 与 `eval-results/run-1QZomX`。这些目录被 Git 忽略，尚不能仅靠仓库链接让第三方复核。发布证据前须脱敏并核对服务端代码版本。

**结论：真实评测可以完成，第二次缓存表仅增加一行；尚不能据此计算真实 HTTP 请求降幅，也不能声称端到端加速。第二次实测耗时反而更长。**

## 2. 修正原报告的推断

- 仓储 Set 使用 upsert：同一个键重复计算后，可以覆盖旧行而不增加行数。因此“行数不涨 = 没调用模型”不成立。
- 数据集包含 30 个语料段落和 30 个问题，而不是 60 个语料段落。仅凭 61 行不能断定各行分别来自语料、查询还是摘要。
- 新增的一行究竟来自什么，缺少逐调用关联证据，不能直接认定为摘要。
- 两次 Recall 不相同。不能仅凭这两个结果认定缓存完全不影响质量，也不能把检索差异直接归因于生成模型随机性。
- 先前独立算法实验、假 provider 实验、真实 HTTP 实验必须分别标注，不能互相替代。

## 3. 已补入的直接计数能力

`internal/models/embedding/measurement.go` 提供按 context 隔离的计数器，观测正式 OpenAI-compatible embedding 调用与缓存查找路径：

| 字段 | 含义 |
|---|---|
| http_attempts | 实际执行 HTTP 客户端调用的次数，包括重试 |
| http_input_items | 每次请求携带的文本条数之和，包括重试重复提交 |
| http_failures | 网络错误或非 2xx 响应次数 |
| memory_hits | 一级内存缓存命中的文本条数 |
| database_hits | 二级数据库缓存命中的文本条数 |
| cache_misses | 未命中的文本条数，包含数据库不可用时的降级 |

使用 `embedding.WithMeasurement(ctx)` 获得实验上下文及计数器；让正式调用链使用该上下文，调用结束后读取 `Snapshot()`。没有启用时不记录。计数器不保存正文、密钥或向量，且支持并发更新。

**当前接入范围：OpenAI-compatible provider 与通用缓存装饰器。** 评测服务已启用计数并存入现有结果 JSON 的 `metric.embedding_measurement`，历史记录不补造零值。它不是所有 provider 通用的计费账本；脱离评测 context 的后台请求不在统计范围内。新版本尚待真实服务端重启与云端实验复核。

## 4. 本轮验证

使用本地 HTTP 测试服务器，并调用正式 OpenAIEmbedder 和 cacheEmbedder，而不是复制缓存算法：

- 冷缓存：两段文本产生 1 次 HTTP 请求、2 条输入；
- 完全重复：命中 2 条内存缓存，0 次 HTTP 请求；
- 部分新增：命中 1 条内存缓存，新增文本产生 1 次 HTTP 请求、1 条输入；
- HTTP 503：明确记录失败，不能当成成功；
- 并发计数与不同上下文隔离测试。

这是正式代码路径的自动化测试，**不是新的云端实测成绩**。

## 5. 下一轮真实实验要求

1. 使用独立实验模型标识或经过验证的隔离缓存，不清空用户共享缓存表。
2. 将计数器接入完整评测上下文，记录建库和查询阶段的覆盖范围；脱离原上下文的后台任务不能默认算已覆盖。
3. 分别测禁用缓存、冷缓存、热缓存和重启后的二级缓存，固定数据集、模型与分块参数。
4. 同时报告 HTTP 请求降幅与文本处理量降幅，分母为零时标记不可计算。
5. 保存脱敏原始结果、服务端版本、配置指纹；至少重复多轮，不凭单次耗时判断提速。
6. 不能用这里的 embedding 缓存命中代替 Wiki 厂商缓存命中率；后者需要独立实验。
